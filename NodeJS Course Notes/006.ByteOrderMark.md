# Byte Order Mark (BOM) — The Practical Guide

> **Quick recap:** the BOM is the Unicode character **U+FEFF** placed at the **very start of a file**. It is invisible to humans but is real bytes to every program that reads the file.
>
> This note is about what the BOM *does to you in practice*: how to spot it, what it breaks, and how to remove it. For the theory (and endianness), see [005](005.BOM_and_Endianness.md).

---

## 1. The bytes to recognise

| Encoding | BOM bytes | Seen in a hex dump as |
|----------|-----------|------------------------|
| UTF-8 | `EF BB BF` | `ï»¿` when read as Latin-1 |
| UTF-16 LE | `FF FE` | `ÿþ` |
| UTF-16 BE | `FE FF` | `þÿ` |
| UTF-32 LE | `FF FE 00 00` | `ÿþ..` |
| UTF-32 BE | `00 00 FE FF` | `..þÿ` |

The UTF-8 BOM is the troublemaker, because UTF-8 is what everything else uses. Its three bytes, misread as Latin-1, appear as the strange text **`ï»¿`** — that is your number-one clue that a file has a BOM.

---

## 2. Why the BOM exists at all

Picture two programs exchanging a UTF-16 file. One writes bytes little-endian, the other expects big-endian. The text arrives as garbage. The BOM solves this by starting the file with a self-describing marker:

```text
FF FE  →  "the low byte comes first"
FE FF  →  "the high byte comes first"
```

**Real-life analogy:** a bilingual form that begins with "this form is in French". You know which rules to read the rest of the document with before you read a single word of content.

For UTF-8 the marker has no ordering job — UTF-8 has no byte order — so it survives only as an "I am UTF-8" label. That label is optional, and most of the world has decided it is unwanted.

## 3. Where you actually meet a BOM

| Source | Why it happens |
|--------|----------------|
| **Windows Notepad** | Its older "UTF-8" option writes a BOM. Newer versions offer "UTF-8" (no BOM) and "UTF-8 with BOM" separately. |
| **Excel / CSV exports** | Excel wants a BOM to recognise UTF-8 CSV as UTF-8; without it, `é` becomes `Ã©`. |
| **PowerShell** (`>` and `Out-File`) | Windows PowerShell 5.1 writes UTF-16LE with a BOM by default. |
| **Some editors and IDEs** | "Save as UTF-8 with BOM" is a one-click option in VS Code, Notepad++, Sublime. |
| **Older PHP / ASP files** | Files created on Windows and uploaded to a Linux server often carry a hidden BOM. |
| **XML tools** | XML allows a BOM and some generators add it. |

**Simple rule of thumb:** if a file was last saved by a Windows tool, there is a decent chance it has a BOM.

## 4. What a BOM breaks

This is why people say "never use a BOM with UTF-8". The bytes are invisible in an editor but very visible to parsers.

### 4.1 The first CSV column gets a weird name

```text
name,age        ← what you wrote
ï»¿name,age     ← what a BOM-less reader sees
```

Your program looks for a column called `name`, finds `ï»¿name`, and crashes with "KeyError: name".

### 4.2 PHP: "headers already sent"

A BOM before `<?php` is **output**. PHP then refuses to send HTTP headers:

```text
Warning: Cannot modify header information - headers already sent by
         (output started at /var/www/index.php:1)
```

The file looks empty on line 1 — the BOM is the invisible culprit. The same thing happens with any language that sends headers after starting output.

### 4.3 A shell script refuses to run

```text
$ ./deploy.sh
bash: ./deploy.sh: /bin/bash^M: bad interpreter: No such file or directory
```

The kernel reads the first bytes looking for `#!`. It finds `EF BB BF # !` and gives up. The `^M` in the message is often a **CRLF** line-ending problem on top of the BOM — both come from Windows editing.

### 4.4 JSON parsers reject it

[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) says implementations **must not add** a BOM to JSON, though they may choose to ignore one. In practice several parsers throw a syntax error on the first character. `JSON.parse()` in JavaScript fails on a BOM-prefixed string.

### 4.5 HTML, CSS, JS and template concatenation

If your build step concatenates files, a BOM sitting in the middle of the output becomes a stray U+FEFF character in the middle of the document — sometimes rendered as a zero-width space in the page.

### 4.6 Makefiles, `.env` files, config files

`KEY=value` with a BOM becomes `\ufeffKEY=value`, so the variable name is wrong and your setting is silently ignored. This one is nasty because nothing errors — it just does not work.

## 5. Detecting a BOM

```bash
# 1. Ask the file command — it usually names the encoding
file index.php
# index.php: PHP script, UTF-8 Unicode (with BOM) text

# 2. Look at the first bytes
hexdump -C index.php | head -1
# 00000000  ef bb bf 3c 3f 70 68 70   ...<?php

# 3. Same idea with od
od -An -tx1 -N3 index.php
# ef bb bf

# 4. Search the whole project for BOMs at the start of files
grep -rl $'^\xEF\xBB\xBF' .
```

```powershell
# Windows PowerShell: show the first bytes
Format-Hex -Path .\file.csv -Count 3
```

---

## 6. Removing a BOM

**Linux / macOS (GNU sed):**

```bash
sed -i '1s/^\xEF\xBB\xBF//' file.csv
```

**Portable, byte-level (removes exactly the first 3 bytes if they are the BOM):**

```bash
tail -c +4 file.csv > file.clean.csv   # only if you know it starts with a BOM
```

**Python — safest, because it understands the encoding:**

```python
# Reading: 'utf-8-sig' silently strips a BOM if present, and works fine without one
with open("file.csv", encoding="utf-8-sig") as f:
    text = f.read()

# Writing without a BOM
with open("out.csv", "w", encoding="utf-8", newline="") as f:
    f.write(text)
```

**Shell, all files in a folder:**

```bash
find . -name "*.php" -exec sed -i '1s/^\xEF\xBB\xBF//' {} +
```

**Editor route:** in VS Code open the file, click the encoding in the bottom-right corner (it shows `UTF-8 with BOM`), choose **Save with Encoding → UTF-8**. In Notepad++: **Encoding → Convert to UTF-8** (not "UTF-8-BOM").

## 7. Adding a BOM on purpose

Sometimes you genuinely want one — most commonly for CSV files that will be opened in Excel.

```bash
# Create a file that starts with the UTF-8 BOM
printf '\xEF\xBB\xBF' > report.csv
printf 'name,age\nAnuj,30\n' >> report.csv
```

```python
with open("report.csv", "w", encoding="utf-8-sig", newline="") as f:
    f.write("name,age\nAnuj,30\n")   # utf-8-sig WRITES the BOM
```

`utf-8` writes plain bytes; `utf-8-sig` adds `EF BB BF` at the start.

## 8. Should this format have a BOM?

| Format | BOM allowed? | Recommendation |
|--------|--------------|----------------|
| **UTF-8 source code** (`.py`, `.js`, `.php`, `.sh`) | Sometimes, but risky | **No** — can break interpreters and headers |
| **JSON** | No (must not be added) | **No** |
| **HTML** | Allowed | **No** — use `<meta charset="utf-8">` instead |
| **XML** | Allowed | Optional; harmless when declared correctly |
| **CSV for Excel** | Allowed | **Yes**, if the file contains non-ASCII text |
| **UTF-16 / UTF-32 files** | Expected | **Yes** — otherwise byte order is a guess |
| **Linux shell scripts** | No | **No** — breaks the `#!` line |

---

## 9. Beyond the start of a file

U+FEFF has a second, older identity: **ZERO WIDTH NO-BREAK SPACE**, a formatting character with no visible width. Its old job (preventing a line break at a space) was removed from Unicode, and now U+FEFF is *supposed* to appear only as a BOM at the start of a file.

If you see a U+FEFF **in the middle** of a document, it is almost always:
- a copy-paste accident, or
- two files concatenated where only one was supposed to have a BOM.

It can be found and removed as a normal character (search for `\uFEFF`).

## 10. Cheat sheet

| Task | Command / fact |
|------|----------------|
| UTF-8 BOM bytes | `EF BB BF` |
| UTF-16 LE / BE BOM | `FF FE` / `FE FF` |
| UTF-32 LE / BE BOM | `FF FE 00 00` / `00 00 FE FF` |
| How it looks when misread | `ï»¿` |
| Detect | `file x` · `hexdump -C x \| head -1` · `od -An -tx1 -N3 x` |
| Remove (one file) | `sed -i '1s/^\xEF\xBB\xBF//' file` |
| Remove (Python read) | `open(f, encoding="utf-8-sig")` |
| Add (Python write) | `open(f, "w", encoding="utf-8-sig")` |
| Add (shell) | `printf '\xEF\xBB\xBF' > file` |
| Classic symptoms | `headers already sent` · `bad interpreter` · wrong first CSV column · ignored `.env` key |

**In one line:** a BOM is a polite label for UTF-16/UTF-32 and an invisible bug factory for UTF-8 — know the three bytes `EF BB BF` and you can diagnose a surprising number of "impossible" errors.
