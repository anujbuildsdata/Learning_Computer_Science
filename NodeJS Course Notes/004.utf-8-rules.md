# UTF-8 Rules — How a Character Becomes Bytes

> A computer does not store letters. It stores **bytes (numbers from 0 to 255)**.
> **Unicode** gives every character in the world a number (called a **code point**, written like `U+0041`).
> **UTF-8** is the set of rules that turns that number into 1, 2, 3 or 4 bytes — and turns those bytes back into the character.

---

## 1. The problem UTF-8 solves

There are two separate questions:

| Question | Answer | Example |
|----------|--------|---------|
| **What** character is this? | A code point (a number) | `A` = U+0041 = 65 |
| **How** do I store that number in a file? | An encoding (a rule set) | UTF-8, UTF-16, UTF-32 |

Without a shared rule, the byte `0xC3` means nothing on its own. UTF-8 says: *"if you see `0xC3` followed by `0xA9`, that is one character: `é`."*

---

## 2. The four patterns

UTF-8 uses **1 to 4 bytes** per character. The **first byte tells you how long the character is**.

| Bytes used | Bit pattern | Code point range | Characters it can cover |
|------------|-------------|------------------|-------------------------|
| **1 byte** | `0xxxxxxx` | U+0000 – U+007F | 128 (plain ASCII) |
| **2 bytes** | `110xxxxx 10xxxxxx` | U+0080 – U+07FF | 1,920 |
| **3 bytes** | `1110xxxx 10xxxxxx 10xxxxxx` | U+0800 – U+FFFF | 63,488 (61,440 usable — 2,048 are surrogates) |
| **4 bytes** | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | U+10000 – U+10FFFF | 1,048,576 |

`x` = **payload bits** — the actual data. Everything else is a fixed signpost.

### How to read a pattern

- `0xxxxxxx` → starts with **`0`** → this is a **whole character by itself**.
- `110xxxxx` → starts with **`110`** → a **2-byte** character starts here; 1 continuation byte follows.
- `1110xxxx` → starts with **`1110`** → a **3-byte** character starts here; 2 continuation bytes follow.
- `11110xxx` → starts with **`11110`** → a **4-byte** character starts here; 3 continuation bytes follow.
- `10xxxxxx` → starts with **`10`** → this is a **continuation byte**. It can never start a character.

> **Easy memory trick:** count the **leading `1` bits** in the first byte — that count is the **total length** of the character. A leading `0` means length 1.
>
> `0…` → 1 byte · `110…` → 2 bytes · `1110…` → 3 bytes · `11110…` → 4 bytes

That `10` prefix is also what makes UTF-8 **self-synchronizing**: if you land on a random byte in a stream, you can find the next character boundary by skipping every byte that starts with `10`.

---

## 3. Why variable length?

**Simple meaning:** common characters get short codes, rare characters get longer ones.

- English text is mostly ASCII, so it stays at **1 byte per letter** — exactly the same size as an old ASCII file. UTF-8 was designed that way on purpose so old files keep working.
- `€`, `अ`, `中` need 3 bytes.
- `😀` needs 4 bytes.

An encoding that always used 4 bytes per character (UTF-32) would make an English file **4× bigger** for no benefit.

## 4. Encoding by hand (step by step)

### Example 1: `A` → 1 byte

```text
Character : A
Code point: U+0041
Decimal   : 65
Binary    : 1000001      (7 bits — fits in 0xxxxxxx)

Pattern   : 0xxxxxxx
Result    : 01000001  =  0x41
```

`A` is a single byte, and it is **identical to ASCII**. That is why UTF-8 is called ASCII-compatible.

### Example 2: `é` → 2 bytes

```text
Character : é
Code point: U+00E9
Decimal   : 233
Binary    : 11101001              (8 bits)

Pattern   : 110xxxxx 10xxxxxx     (11 payload bits available)
Pad to 11 : 00011101001
Split     : 00011 | 101001        (5 bits + 6 bits)

Byte 1    : 110 00011  =  0xC3
Byte 2    : 10  101001 =  0xA9
Result    : C3 A9
```

### Example 3: `€` → 3 bytes

```text
Character : €
Code point: U+20AC
Binary    : 0010000010101100      (16 bits)

Pattern   : 1110xxxx 10xxxxxx 10xxxxxx   (16 payload bits)
Split     : 0010 | 000010 | 101100       (4 + 6 + 6)

Byte 1    : 1110 0010  =  0xE2
Byte 2    : 10  000010 =  0x82
Byte 3    : 10  101100 =  0xAC
Result    : E2 82 AC
```

### Example 4: `😀` → 4 bytes

```text
Character : 😀
Code point: U+1F600
Binary    : 000011111011000000000    (21 bits — this is why 4 bytes are needed)

Pattern   : 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx   (21 payload bits)
Split     : 000 | 011111 | 011000 | 000000        (3 + 6 + 6 + 6)

Byte 1    : 11110 000  =  0xF0
Byte 2    : 10  011111 =  0x9F
Byte 3    : 10  011000 =  0x98
Byte 4    : 10  000000 =  0x80
Result    : F0 9F 98 80
```

> Notice: the first byte never lies. It always announces the total length, so a decoder just reads N bytes and strips the fixed prefix bits.

| Character | Code point | UTF-8 bytes | Bytes used |
|-----------|------------|-------------|------------|
| `A` | U+0041 | `41` | 1 |
| `~` | U+007E | `7E` | 1 |
| `©` | U+00A9 | `C2 A9` | 2 |
| `é` | U+00E9 | `C3 A9` | 2 |
| `अ` | U+0905 | `E0 A4 85` | 3 |
| `€` | U+20AC | `E2 82 AC` | 3 |
| `中` | U+4E2D | `E4 B8 AD` | 3 |
| `😀` | U+1F600 | `F0 9F 98 80` | 4 |
| `🚀` | U+1F680 | `F0 9F 9A 80` | 4 |

**Note:** the byte count is *not* the same as the visible size of the character in an editor, and not the same as a programming language's `string.length` (see below).

## 6. The strict rules a decoder enforces

1. **Continuation bytes must start with `10`.** A byte that starts with `10` is never the start of a character.
2. **The shortest form must be used.** Writing `A` as a 2-byte overlong sequence (`C1 81`) is illegal. Overlong forms are also a security problem: a filter that blocks the byte for `/` may still let its overlong version through.
3. **Surrogates are forbidden.** Code points `U+D800`–`U+DFFF` are reserved for UTF-16 internals and must never appear in UTF-8.
4. **Nothing above `U+10FFFF`.** That is the highest code point Unicode defines.
5. **No character is longer than 4 bytes.** Anything starting `11111…` is invalid.

If you see `EF BF BD` in a file, that is the **replacement character `�` (U+FFFD)** — the decoder found invalid bytes and substituted it. And `EF BB BF` at the very start of a file is the **BOM** (see [005](005.BOM_and_Endianness.md)).

---

## 7. Why developers like UTF-8

| Reason | Meaning |
|--------|---------|
| **ASCII-compatible** | Any ASCII file is already valid UTF-8. No conversion needed. |
| **No endianness** | Bytes are read in order, so there is no "little vs big" problem. |
| **Self-synchronizing** | After a corrupted byte you can resync at the next start byte. |
| **Space-efficient** | Most real-world text is ASCII → 1 byte per character. |
| **Standard everywhere** | HTML, JSON, Linux and most APIs default to UTF-8. |

## 8. Common mistakes

**Mistake 1 — counting bytes and calling them characters.**

```js
"😀".length;                      // 2   ← JavaScript counts UTF-16 units, not characters
[..."😀"].length;                 // 1   ← correct: spread counts code points
Buffer.byteLength("😀", "utf8");  // 4   ← the real UTF-8 byte count
```

**Mistake 2 — slicing a string in the middle of a character.**
Cutting 4 bytes down to 3 leaves half a character, which shows up as `�` when read back.

**Mistake 3 — assuming file size equals text length.**
1000 English characters ≈ 1000 bytes. The same text full of emoji can be several times larger.

**Mistake 4 — mixing encodings.**
`é` written as UTF-8 is `C3 A9`. Read as ISO-8859-1, those two bytes become `Ã©`. That strange "mojibake" text is almost always an encoding mismatch, not corrupted data.

## 9. Summary

| Rule | Meaning |
|------|---------|
| 1 byte | `0xxxxxxx` → U+0000–U+007F (ASCII) |
| 2 bytes | `110xxxxx 10xxxxxx` → up to U+07FF |
| 3 bytes | `1110xxxx 10xxxxxx 10xxxxxx` → up to U+FFFF |
| 4 bytes | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` → up to U+10FFFF |
| Continuation | Every following byte starts with `10` |
| Signpost | Leading `1` bits in byte 1 = total character length |
| Maximum | 4 bytes, `U+10FFFF` |

- Unicode gives each character a **number**; UTF-8 decides **how to store that number as bytes**.
- The first byte announces the length; continuation bytes carry the rest of the payload.
- Shortest form wins, surrogates are banned, and `EF BB BF` at the start is a BOM, not text.
