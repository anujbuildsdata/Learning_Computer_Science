# Byte Order Mark (BOM) and Endianness

> Two ideas that always travel together:
>
> - **Endianness** = *in which order do I write the bytes of a multi-byte number?*
> - **BOM** = *a tiny marker at the start of a file that announces "here is the encoding, and here is the byte order".*

---

## Part 1 — Endianness

### The problem

A single byte (`0x41`) has no order problem. But a **multi-byte** value like `0x12345678` is four bytes: `12`, `34`, `56`, `78`. When the computer writes them to memory or to a file, it has to pick a direction.

**Real-life analogy:** the date **24/10/2026** and **10/24/2026** contain the same three numbers. If the reader does not know the convention, the date is ambiguous. Endianness is exactly that convention — for bytes.

### Little Endian

The **least significant byte (LSB)** — the "small end" of the number — is stored **first**.

```text
Value      : 0x12345678
Stored as  : 78 56 34 12
             ↑           ↑
        smallest      biggest
         byte          byte
```

Used by **Intel and AMD (x86)** processors, and by **ARM in its usual (little-endian) mode**.

### Big Endian

The **most significant byte (MSB)** — the "big end" — is stored **first**.

```text
Value      : 0x12345678
Stored as  : 12 34 56 78
             ↑           ↑
        biggest       smallest
         byte          byte
```

Used by **network protocols** (this is why it is called **network byte order**) and by some older systems (SPARC, PowerPC in big-endian mode).

### Side-by-side memory view

```text
Address : 0x100  0x101  0x102  0x103
Little  :  78     56     34     12
Big     :  12     34     56     78
```

### Which is better?

| | Little Endian | Big Endian |
|---|---|---|
| **Readability for humans** | Hard — bytes look reversed | Easy — same order as you write the number |
| **Maths and casting** | Convenient: the low byte sits at the low address, so truncating a number is cheap | Slightly less convenient |
| **Who uses it** | x86, ARM (default), most phones and PCs | Network byte order, some RISC servers |

Neither is "correct". They are just two agreed conventions, and **both sides must agree** or the number arrives scrambled (`0x12345678` read with the wrong order becomes `0x78563412`).

### How to check your own machine

```bash
# Python
python3 -c "import sys; print(sys.byteorder)"     # little or big

# Node.js
node -e "console.log(require('os').endianness())"  # LE or BE

# Linux
lscpu | grep -i "byte order"
```

### The programmer's rule

When sending numbers over a network, convert to **network byte order (big endian)** first:

```c
uint32_t net_value = htonl(host_value);   // host → network
uint32_t host_value = ntohl(net_value);   // network → host
```

`htonl` / `ntohl` do nothing on a big-endian machine and swap the bytes on a little-endian one — that is the whole point.

## Part 2 — BOM (Byte Order Mark)

### What it is

The **Byte Order Mark** is one specific Unicode character: **U+FEFF**, written at the **very beginning** of a text file.

It is a real character, but it is **not supposed to be visible text** — it is a label for the reader.

**Real-life analogy:** a shipping label on the outside of a box. It tells the courier how to handle the parcel; it is not part of what is inside the box.

### What the BOM announces

| Question | BOM answers it |
|----------|----------------|
| Which encoding is this file? | UTF-8 / UTF-16 / UTF-32 |
| If the encoding is multi-byte, which byte order? | Little endian or big endian |
| Should I read bytes left-to-right or grouped? | Depends on the above |

### BOM bytes per encoding

| Encoding | BOM bytes | Meaning |
|----------|-----------|---------|
| **UTF-8** | `EF BB BF` | "I am UTF-8" (byte order is irrelevant) |
| **UTF-16 LE** | `FF FE` | "I am UTF-16, little endian" |
| **UTF-16 BE** | `FE FF` | "I am UTF-16, big endian" |
| **UTF-32 LE** | `FF FE 00 00` | "I am UTF-32, little endian" |
| **UTF-32 BE** | `00 00 FE FF` | "I am UTF-32, big endian" |

> **Why is UTF-16's BOM "FF FE" or "FE FF" and not some new pattern?** Because it is literally the character U+FEFF encoded in that byte order. If you read `FF` first, you know the file's low byte comes first → little endian. The marker describes itself.

> **Careful with UTF-32 LE vs UTF-16 LE.** Both start with `FF FE`. The extra `00 00` confirms UTF-32, so a reader must look at more than two bytes to be sure.

### Why UTF-8 usually has no BOM

UTF-8 is **byte-oriented**: a character is always stored one byte after another, so there is no byte order to announce. The encoding can also be recognised from the byte pattern itself, and UTF-8 files are supposed to be readable by any ASCII tool.

So for UTF-8 the BOM is **optional and generally discouraged** — it often causes bugs (see [006](006.ByteOrderMark.md)).

## Part 3 — How they work together

### Example: the letter `A` in UTF-16

`A` is U+0041, so its 16-bit value is `0x0041`. Written to a file:

```text
UTF-16 LE : 41 00    (low byte first)
UTF-16 BE : 00 41    (high byte first)
```

Both look like two bytes; only the order differs. Without a BOM, a reader that guesses wrong sees `0x4100` — a completely different character (a CJK ideograph), not `A`. **That is the entire reason the BOM exists.**

### Step by step, how a program reads a file

```text
1. Read the first bytes.
2. FF FE   → UTF-16 little endian → decode the rest accordingly
   FE FF   → UTF-16 big endian
   00 00 FE FF → UTF-32 big endian
   EF BB BF → UTF-8 (and skip these 3 bytes, they are not text)
   none of the above → guess UTF-8 (modern default) or ask the user
3. Decode the rest of the file using that rule.
```

### Example: a UTF-16LE file containing "Hi"

```text
FF FE 48 00 69 00
└─┬─┘ └──┬──┘└──┬─┘
 BOM     H      i
```

Without the BOM, a reader could interpret `48 00` as `0x0048 + a null character`, and the text would come out as `H\0i\0` — the classic "null bytes everywhere" look of a UTF-16 file opened as ASCII.

## Part 4 — Endianness beyond text

Endianness is not only a text-file issue. Every binary format has to choose an order:

| Format | Byte order |
|--------|------------|
| **PNG** | Big endian (specified in the spec) |
| **JPEG** | Big endian |
| **BMP, GIF** | Little endian |
| **ELF executables** | Header says which order the file uses |
| **TCP/IP headers** | Big endian (network byte order) |
| **Java `.class` files** | Big endian |
| **Windows `.exe` (PE)** | Little endian |

If you ever parse a binary file and the numbers look absurd (`0x00010000` instead of `1`), suspect endianness first.

## Part 5 — Comparison table

| Aspect | Description | Where it applies |
|--------|-------------|------------------|
| **BOM** | Character U+FEFF at the start of a file, signalling encoding and byte order | Optional in UTF-8, useful in UTF-16/UTF-32 |
| **Endianness** | The order in which the bytes of a multi-byte value are stored | Any multi-byte encoding or binary format |
| **Little endian** | Least significant byte first | x86, ARM, most consumer hardware |
| **Big endian** | Most significant byte first | Network protocols, some servers, PNG/JPEG |
| **Network byte order** | Another name for big endian when used on the wire | `htons` / `htonl` in sockets |

---

## Summary

- **Endianness is a convention, not a quality.** Little and big endian are both correct as long as both sides agree.
- `0x12345678` is `78 56 34 12` in little endian and `12 34 56 78` in big endian.
- **Networks use big endian**, so convert before sending.
- A **BOM** is U+FEFF at the start of a file; `EF BB BF` for UTF-8, `FF FE` for UTF-16LE, `FE FF` for UTF-16BE.
- UTF-16/UTF-32 **need** a BOM (or a declared encoding) because byte order is otherwise ambiguous.
- UTF-8 does **not** need one — and in web files it usually causes more problems than it solves.
